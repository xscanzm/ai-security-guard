# 泄露应急：发现漏了，前 48 小时做什么

## 先说结论

发现泄露后，最贵的动作是“再观察一下”。**先止血，再查范围，再通知，最后复盘。** 顺序反了，损失会扩大。

下面按时间线走。不要求你全做到，但每一步都别跳过。

---

## 第 0–1 小时：止血

| 泄露类型 | 第一个动作 |
| --- | --- |
| API Key / Token | 去平台**吊销**，不是改代码 |
| 数据库密码 | 改密码，踢掉现有连接 |
| 客户名单/合同 | 撤回共享链接，改权限，停止同步 |
| Skill 外传数据 | 断网、卸载 Skill、关掉相关 MCP |
| 代码进了公开仓库 | 先转私有，再清历史（见下） |
| 员工电脑被装后门 | 断网，保留现场，别急着重装 |

**不要做的事**

- 不要先删日志。
- 不要先和攻击者对话。
- 不要为了“别让老板知道”拖到第二天。

---

## 第 1–6 小时：查范围

回答四个问题：

1. **什么泄露了？** 密钥、客户信息、代码、合同？
2. **泄露到哪？** 公网、微信群、网盘、外包、前员工？
3. **持续多久？** 什么时候发的，什么时候发现的？
4. **谁可能看过？** 下载记录、访问日志、群成员。

能查的记录：

- Git 历史：`git log -p --all -- .env`
- 平台审计日志：API 调用记录、登录 IP
- `.ai-guard/hook.log`：AI 工具拦截记录
- 网盘/文档的分享记录
- 聊天工具的文件下载记录

---

## 第 6–24 小时：处置

### 密钥

1. 吊销旧 key。
2. 生成新 key，只放进 `.env` 或密钥管理服务。
3. 检查账单和调用记录，看有没有被滥用。
4. 如果 key 有子权限，一并检查。

### 客户信息

1. 撤回/删除公开文件。
2. 评估是否触发合同里的通知义务。
3. 涉及身份证、银行卡的，按《个人信息保护法》评估是否要通知个人和监管。
4. 留好处理记录。

### 代码

1. 仓库转私有。
2. 从历史里删除敏感文件（`git filter-repo` 或 BFG），**force push**。
3. 通知所有克隆过仓库的人重新克隆。
4. 假设旧历史已经泄露，吊销其中所有密钥。

**注意**：GitHub 上的 fork、缓存、CI 日志可能仍有旧内容。删历史不是万能的。

---

## 第 24–72 小时：复盘

只问三个问题：

1. **哪个动作导致的？** 不是“谁”，是“哪个流程”。
2. **为什么没拦住？** 没有检查、检查太晚、权限太大、还是没人负责？
3. **改什么流程？** 具体到“下次发版前跑什么命令”。

复盘输出一页纸：

```text
事件：
时间：
泄露内容：
影响范围：
止血动作：
根因：
改进项（负责人/截止时间）：
```

---

## 一张速查表

```text
发现泄露
  → 吊销/改密/撤回（0–1h）
  → 查日志/范围（1–6h）
  → 通知/处置（6–24h）
  → 复盘/补流程（24–72h）
```

---

## 最后一句

泄露不是“运气不好”，是流程里有一个没人负责的口子。应急的价值不是把这次糊过去，是让下一次在发生前被拦住。
